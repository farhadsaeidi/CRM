# ساخت رابط کاربری در CRM

این اسکیل قراردادهای بصری و ساختاری پروژه را جمع کرده تا هر بار از نو کشف نشوند.
برای معماری کلی به `.claude/architecture.md` و برای قواعد همیشگی به `CLAUDE.md` مراجعه کنید.

> پروژه فعلاً اسکلت است: فقط `Home` موقت و `NotFound` وجود دارند. تمِ کامل ولی آماده است.

## ۱. پیش از هر تغییر بصری

مقدار واقعی رنگ‌ها را بخوانید — نام‌ها معنایی نیستند و حدس زدن به انتخاب غلط می‌انجامد:

```bash
grep -n "color-var-color-" frontend/src/index.css | head -60
```

برای افزودن رنگ تازه، بیشترین شماره را پیدا کنید و بعدی را بسازید:

```bash
grep -oE "^\s*--color-var-color-[0-9]+" frontend/src/index.css | grep -oE "[0-9]+$" | sort -n | tail -1
```

## ۲. تلهٔ RTL

صفحه `dir="rtl"` است. دو چیز خلاف شهود عمل می‌کنند:

| هدف | کلاس درست |
|---|---|
| هل دادن به لبهٔ **چپ** (انتهای خط) | `mr-auto` |
| هل دادن به لبهٔ **راست** (ابتدای خط) | `ml-auto` |

مارجینِ `auto` فضای خالی را در همان سمتِ خودش جمع می‌کند و عنصر را به سمت مخالف می‌راند.

ترتیب DOM هم برعکس دیده می‌شود: اولین فرزندِ یک فلکس، **راست‌ترین** است. هنگام چیدن
دکمه‌ها ترتیب را از راست به چپ بنویسید.

آیکون‌های جهت‌دار باید معکوس شوند: بازگشت = `FiArrowRight`، نه `FiArrowLeft`.

## ۳. Tailwind نسخهٔ ۴

- `@import "tailwindcss";` و بلافاصله `@custom-variant dark (&:where(.dark, .dark *));`
- تم در `@theme` — **هیچ `tailwind.config.js` نسازید.** اگر ساخته شود، Tailwind نادیده‌اش
  می‌گیرد ولی PyCharm آن را می‌خواند و تم را اشتباه می‌فهمد.
- مقدار پویا با متغیر CSS: `style={{"--x": ...}}` و کلاس `w-(--x)`.
- کلاس‌هایی که با رقم شروع می‌شوند در CSS اسکیپ می‌شوند (`2xs:` → `.\32 xs\:`)؛
  هنگام grep زدن روی CSS خروجی به این دقت کنید.

تمِ دارک قبل از اولین رندر در `index.html` اعمال می‌شود (اسکریپت کوچکِ inline)، تا
صفحه‌های بدون هدر فلاشِ لایت نداشته باشند. اگر سوییچرِ تم را جابه‌جا کردید، آن اسکریپت
باید سرِ جایش بماند.

## ۴. جدول‌ها

دو یوتیلیتی از قبل در `index.css` هست و ستون‌بندیِ دو جدول اصلی را تعریف می‌کند:

- `grid-customer` — پنج ستون: نام، شماره تماس، تاریخ، وضعیت، عملیات
- `grid-transaction` — چهار ستون: ردیف، نسیه، پرداختی، عملیات

ستون عملیات عمداً باریک (`0.1fr`–`0.2fr`) و ستون نام پهن (`1fr` با کفِ `12rem`) است.
به‌جای `<table>` از گریدِ CSS استفاده می‌شود تا سطرها بتوانند کارت شوند و در موبایل
بشکنند. اگر ستونی اضافه شد، همین دو کلاس را ویرایش کنید نه اینکه در JSX گرید تازه بنویسید.

## ۵. زبان بصری

- سطوح: سفید (`var-color-00`) در لایت، `var-color-36/37` در دارک
- بوردر استاندارد: `var-color-02` در لایت، `var-color-38` در دارک
- پس‌زمینهٔ صفحه: `var-color-49` در لایت و `var-color-35` در دارک، با بافتِ `bg-dotted`
- اکسنت: `var-color-15` (#00bcff)
- وضعیت‌ها: بستانکار → سبز (`31`)، بدهکار → قرمز (`28`)، بی‌حساب → خاکستری (`04`)
- **سایه ندارند.** جداسازی فقط با رنگ و بوردر. سایه فقط برای مودال‌ها.
- فونت‌ها: `font-IRANSansXFaNumRegular` و برای تأکید `Medium` / `DemiBold` / `Bold`

کلاس‌های آمادهٔ فرم: `form-container`، `input` + (`input-bluish` | `input-purplish` |
`input-error`)، `btn` + (`btn-bluish` | `btn-purplish`).

هر چیزی که می‌سازید باید در **هر دو تم** درست باشد. بعد از تغییر، هر دو را چک کنید.

## ۶. تله‌های تکرارشونده

- `:hover` روی `disabled` هم اعمال می‌شود → `enabled:hover:...`
- کامنت JSX بین صفت‌ها نامعتبر است → بالای عنصر
- خطای DRF در کلید `detail` می‌آید → در `catch` اول آن را بخوانید
- `overflow-hidden` روی کارت، عناصر مطلقِ لبه را می‌بُرد
- رشته‌های حاوی `\\` را با ابزار Write بنویسید، نه heredoc — heredoc بک‌اسلش‌ها را
  می‌خورد و مثلاً `"\\s"` در `api/client.js` به `"\s"` تبدیل و رجکس خراب می‌شود

## ۷. راستی‌آزمایی — بدون مرورگر

> **از ابزارهای مرورگر استفاده نکنید.** فرهاد (۱۴۰۵/۰۵/۳۱) خواست بازبینیِ مرورگر
> کلاً کنار گذاشته شود؛ هر فراخوانی برای او یک پرسشِ مجوز می‌ساخت. راستی‌آزمایی
> باید از روی **CSS بیلدشده** انجام شود که هم قطعی‌تر است هم بی‌سروصدا.

سه دلیل که پنلِ مرورگر برای این کار ابزارِ خوبی هم نبود:
- وقتی پنل نمایش داده نمی‌شود صفحه فریم نمی‌سازد و **ترنزیشن‌ها پیش نمی‌روند**؛
  `getComputedStyle` مقدارِ قدیمی را می‌دهد و شبیهِ باگِ رنگ دیده می‌شود.
- به همین دلیل انیمیشن‌ها هم فریز می‌مانند (مثلاً `modal-in` روی `scale(0.05)`،
  که عرضِ ۴۸۰ پیکسلی را ۲۴ گزارش می‌کرد).
- `:focus` اصلاً مچ نمی‌شود چون پنجره فوکوسِ سیستمی ندارد، پس استایل‌های فوکوس
  قابلِ اندازه‌گیری نیستند.

روشِ درست — قاعده را از خودِ CSS خروجی بخوانید. توجه: `:` در نامِ کلاس اسکیپ
می‌شود (`hover:bg-x` → `hover\:bg-x`)، پس grepِ ساده چیزی پیدا نمی‌کند:

```bash
cd frontend && npm run build && ../venv/bin/python - <<'PY'
import glob, re
css = open(glob.glob("dist/assets/index-*.css")[0], encoding="utf-8").read()
for cls in ["hover:bg-var-color-01", "dark:hover:bg-var-color-40"]:   # کلاس‌های موردنظر
    esc = re.escape(cls.replace(":", "\\:"))
    for rule in re.findall(r"[^{}]*" + esc + r"[^{]*\{[^}]*\}", css)[:1]:
        print(rule.strip())
PY
```

این روش هم می‌گوید قاعده اصلاً تولید شده یا نه (کلاسِ تایپی‌خورده هیچ خروجی ندارد)،
هم نشان می‌دهد زیر کدام شرط اعمال می‌شود — مثلاً `:where(.dark, .dark *)` برای
قواعدِ تمِ دارک، که همان چیزی است که بابتش رنگِ دارک در تم لایت نشت می‌کند.

همیشه هر دو را اجرا کنید — بیلد گاهی خطایی را رد می‌کند که ESLint می‌گیرد:

```bash
cd frontend && npx eslint src/ && npm run build
```
